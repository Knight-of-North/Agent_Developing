# 《AI 剧本杀》优化方案书

> 版本：v1.0
> 日期：2026-11-12
> 依据：当前仓库实现 + GitHub 公开项目调研（README、功能说明与仓库结构，未直接复制代码）
> 目标：在不推翻现有 LangGraph + Streamlit 架构的前提下，提升玩法深度、AI 可解释性和演示表现力。

---

## 0. 结论摘要

当前项目已经是一个**完成度较高的多智能体剧本杀应用**：15 个 LangGraph 节点、interrupt 人在回路、按角色隔离的短期记忆、确定性规则层、167 个测试、完整的开始页/选角/对话/投票/复盘流程。

和开源参考项目相比，当前最大的差距不在“Agent 数量”或“图编排”，而在三处：

1. **玩法深度**：缺少私聊、场景搜证、证物出示/组合等“侦探动作”，玩家主要仍在“群聊 + 投票”。
2. **AI 辅助**：缺少 AI 侦探搭档/笔记分析，玩家需要自己记忆和整理大量线索。
3. **表现力**：Streamlit 暗色档案风已经不错，但缺少角色立绘、证物卡、昼夜/场景过渡、旁观/回放等“戏剧化”呈现。

本方案建议：

- **答辩前**：不重写、不引入新基础设施，只做演示与稳定性收尾；
- **答辩后 1–2 周**：优先做 **AI 侦探助手、场景搜证、私聊** 三项；
- **长期**：再做证物组合、剧本库/编辑器、角色立绘、旁观/回放与玩法指标。

一句话取舍：

> **继续强化“多智能体 + 信息差 + 人在回路”，不把项目改造成 React/3D 展示工程。**

### 1.1 这些项目共同证明的三件事

1. **“多智能体 + 社交推理”是成立的产品方向**，不是硬凑概念；
2. **玩家最在意的是“信息差 + 行动反馈”**，而不是 Agent 数量；
3. **纯聊天很容易腻**，搜证、私聊、证物、复盘等“侦探动作”决定游戏深度。

## 2. 当前项目基线

### 2.1 已经具备的能力

| 能力 | 当前实现 | 评价 |
|---|---|---|
| 多智能体编排 | [graph.py](../graph.py) 15 节点 StateGraph，条件边路由 | 与 nison/LieGraph 同路线，架构成立 |
| 人在回路 | choose_role / human_turn / human_vote / human_tiebreak 均用 interrupt | 比多数 demo 完整 |
| 角色记忆 | [game_state.py](../game_state.py) 的 agent_memory，[nodes.py](../nodes.py) 每角色保留最近 3 条发言 | 够用，且不烧大量 token |
| 信息差 | 私密线索 / 公开线索 / 隐藏线索三层 | 设计正确，是核心优势 |
| 确定性规则 | 计票、校验、防泄露、名单过滤全在 Python | 可测试、可解释 |
| 测试 | 167 个测试通过，ruff 全绿 | 本科项目中偏上 |
| UI | 暗色档案风、开始页、选角、阶段幕布、氛围音、复盘卡、侦探笔记 | 已有辨识度，不必重写 |

### 2.2 当前主要短板

1. **玩家动作少**：主要是发言、公开线索、指控、调查、投票；缺少“私聊套话、场景搜证、证物出示”。
2. **线索呈现偏列表**：有线索板，但没有“证物卡/证物组合/出示反应”的戏剧性。
3. **AI 辅助缺位**：玩家要自己从长对话中整理矛盾，容易疲劳。
4. **剧本是一次性的**：没有剧本库/预设/编辑器，重玩和演示成本高。
5. **表现层偏“网页应用”**：缺少角色立绘、场景切换、旁观/回放等“舞台感”。
6. **玩法指标缺失**：有工程测试，但没有胜率、指认准确率、发言多样性等游戏质量数据。

## 4. 设计原则与关键取舍

### 4.1 三条路线比较

| 路线 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 现有 Streamlit 增强 | 保留图/状态/UI，增加组件与节点 | 风险低、复用 167 测试、答辩前可控 | 视觉上限不如 React | **推荐** |
| B. React + FastAPI 重写 | 照 Scottish 重做前后端 | 视觉/交互上限高 | 2 周内无法稳定交付，现有测试与 UI 全部重做 | 课程后考虑 |
| C. 3D/语音/旁观 | 照 Wolfcha/AI Mafia 做 3D/语音 | 演示震撼 | 成本高、与“智能体”评分无关、容易翻车 | 不做 |

### 4.2 明确不做什么

- **不引入 Milvus/RAG/MySQL/Redis**：当前单局状态用 GameState + agent_memory + checkpointer 足够；引入向量库会增加部署复杂度，对课程演示收益很低。
- **不重写 React/Three.js**：现有 Streamlit 已经能讲清楚架构和玩法；重写不会让“智能体”更成立。
- **不做多 LLM 适配**：DeepSeek 单模型足够，成本可控，避免答辩现场多供应商配置出错。
- **不做 AI 生图/语音**：生成图片/语音会引入外部服务和版权/延迟问题，收益低于玩法增强。

### 4.3 关键决策

1. **先玩法、后视觉**：评委更容易记住“能私聊/能搜证/有 AI 助手”，而不是多一个渐变背景。
2. **先低风险组件、后图结构改造**：AI 助手、笔记、复盘卡不改变图，优先做；私聊/搜证涉及状态机，放到答辩后。
3. **复用现有动作协议**：human_turn_node 已有 reveal_clue / accuse / investigate / silence 的结构化 action，扩展新玩法时沿用同一协议，避免再造一套控制流。

## 6. 详细方案

### 6.1 P1：AI 侦探助手（最推荐，4–6 小时）

**参考**：Scottish 的 AI 搭档、Zewang 的 Summary Agent。

**目标**：玩家点击“让助手分析”后，AI 根据**公开线索 + 玩家自己的推理笔记**给出 3–5 条“可疑点 / 建议盘问对象”，不直接说出真相。

**实现建议**：

- 新增 prompts.build_detective_assistant_prompt()；
- 输入只包含：公开线索、玩家笔记、公开人物关系、当前轮次；
- 不传入 script.murderer、script.truth、私密线索；
- 侧边栏按钮：🧠 让助手分析当前线索；
- 结果用 st.info 或小卡片展示，并缓存相同输入的响应，避免重复烧 token；
- 可选：输出 3 条“下一步建议”，每条不超过 40 字。

**优点**：

- 不改变 graph.py，风险最低；
- 演示效果强，玩家能感知“AI 在帮我推理”；
- 可以复用现有 prompts.py / _safe_llm_text / API 配置。

**缺点/权衡**：

- 每次点击会增加一次 LLM 调用（约 ¥0.01–0.03/次）；
- 如果上下文过滤不严，可能泄露真相，必须白名单输入；
- 不能替代玩家决策，否则游戏变得无聊。

**验收**：

- 响应 < 8 秒；
- 输出不含真凶姓名/真相原文；
- 167 个测试保持通过，新增至少 2 个 prompt 隔离测试。

### 6.2 P1：场景搜证地图（1–2 天）

**参考**：Zewang 的可视化场景地图、nison 的搜证阶段。

**目标**：把现在“暗中调查现场”按钮升级成“地点选择 + 搜证卡”，让玩家感觉自己在探索现场。

**实现建议**：

- 在剧本生成 schema 增加可选字段：

~~~json
{
  "locations": [
    {"name": "书房", "desc": "死者的书房", "clue_ids": ["c1", "c2"]},
    {"name": "花园", "desc": "雨后泥泞的花园", "clue_ids": ["c3"]}
  ]
}
~~~

- human_turn_node 的 investigate action 扩展为 {"action": "investigate", "location": "书房"}；
- 没有 locations 的旧剧本自动回退为原来的随机调查；
- UI 用 3–4 张卡片显示“已搜 / 未搜 / 剩余次数”；
- 每次搜证只返回该地点尚未发现的线索。

**优点**：

- 复用现有隐藏线索和 investigated_clues 状态，不需要新图节点；
- 视觉和玩法同时提升，适合截图/演示；
- 失败时可回退到旧逻辑，风险可控。

**缺点/权衡**：

- 剧本生成 prompt/schema 要改，旧剧本需要兼容；
- 生成 3–4 个地点会增加约 5–10% 的生成 token；
- 要防止地点线索重复/全部集中在同一地点。

**验收**：

- 每局至少 3 个地点、4–6 条线索；
- 同一线索不重复出现；
- 旧格式剧本不报错；
- 新增 5+ 个纯函数测试（地点解析/线索分配/回退）。

### 6.3 P1：私聊套话（1–2 天，答辩后做）

**参考**：nison 的私聊阶段、Wolfcha 的 table-aware memory。

**目标**：玩家可以单独找某个嫌疑人“密聊”，套出不愿在群里说的信息。

**两种实现**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. UI-only 密聊 | 直接把玩家消息和 AI 回复存到 private_messages，不改图 | 1 天内可做，风险低 | AI 不参与轮次，信息可能和主线脱节 |
| B. Graph 私聊节点 | 新增 private_chat 节点 + interrupt，AI 回复后回到讨论 | 真正影响游戏状态，玩法完整 | 需要改图、状态、UI、测试，1–2 天 |

**推荐**：答辩后选 B；如果只想答辩演示，选 A 并明确“这是展示原型”。

**关键约束**：

- 私聊内容只对玩家可见，不能进入公共 messages；
- 私聊不能把凶手的 secret 直接交给 LLM 复述；
- 私聊次数建议每轮 1 次，避免无限套话；
- 私聊会让 token 成本上升约 10–20%。

### 6.4 P2：证物出示/组合（2–4 天）

**参考**：Scottish 的证物系统（类似《逆转裁判》）。

**目标**：把“线索”从列表升级为可出示、可组合的“证物卡”。

**实现建议**：

- 证物数据：id / name / desc / tags / related_suspects；
- 玩家在指控/发言时选择“出示证物”；
- AI 根据证物标签生成反应；如果证物击中凶手秘密，触发额外反应；
- 组合：两条线索合成一条新结论（可选，后期做）。

**优点**：戏剧性最强，最适合答辩演示。
**缺点**：需要新的状态、验证、AI 反应和防剧透；工期长，**不建议答辩前做**。

### 6.5 P2：嫌疑度/信念面板（2–3 小时）

**参考**：LieGraph 的 suspicion matrix。

**目标**：让玩家在侧边栏给每个嫌疑人打“嫌疑度”，从“记忆负担”变成“可视化推理”。

**实现建议**：

- 每个嫌疑人一个 0–100 slider，状态存在 st.session_state；
- 每局按 thread_id 隔离，避免跨局残留；
- 可按嫌疑度排序显示“当前最可疑”；
- 不把玩家打的分数传给 AI（避免 AI 迎合玩家）。

**优点**：低成本、直观；**缺点**：只是辅助 UI，不改变规则。
**建议**：P1 级小功能，可与 AI 助手一起做。

### 6.6 P2：预设剧本库（4–8 小时）

**参考**：Scottish 的剧本库/预设、Zewang 的剧本大厅。

**目标**：提供 3 个内置案件（民国豪门 / 校园怪谈 / 科幻末世），一键开始，不用每次等生成。

**实现建议**：

- 在 docs/presets/ 放 3 个 JSON（角色、关系、线索、真相）；
- 开始页加“快速开始：预设案件”按钮；
- 预设案件走 generate_script_node 的跳过逻辑（已有 if script 分支），不调生成 LLM；
- 校验仍走 validators。

**优点**：答辩演示稳定、可重复；**缺点**：需要人工写/审 3 个剧本，工作量在内容不在代码。

### 6.7 P2：角色立绘与氛围（按阶段）

**参考**：Wolfcha 的角色立绘/昼夜/语音、AI Mafia 的镜头感。

**低成本做法**：

- 用“首字头像 + 渐变色 + 身份标签”的 CSS 卡片，不接图片服务；
- 角色卡增加“公开身份/与死者关系/嫌疑标签”；
- 继续使用现有阶段幕布 + 氛围音；
- 复盘页使用“案件卷宗”卡片布局。

**高成本做法**（不建议短期）：

- AI 生成角色头像/封面；
- 语音合成；
- 3D/体素场景；
- 旁观模式/回放。

**权衡**：视觉是加分项，不是智能体项目的核心评分项；在答辩前投入产出比低。

### 6.8 P2：跨局统计与复盘（2–3 小时）

**参考**：LieGraph 的 metrics、Wolfcha 的 post-game review。

**目标**：记录最近 5–10 局的“胜负 / 你的角色 / 指认是否正确 / 对话轮数”，在开始页展示。

**实现建议**：

- st.session_state.game_history 列表，每局结束 append；
- 开始页“最近战绩”小卡片；
- 不做数据库，不跨浏览器；
- 已有复盘卡/JSON 导出可直接复用。

**优点**：演示“项目有数据闭环”；**缺点**：没有长期分析价值，适合课程展示。

## 8. 验收指标

### 8.1 技术指标

- pytest -q 保持 167+ 通过；
- ruff check . 零错误；
- 新功能不改变已有 15 节点主流程（除新增可选节点）；

### 8.2 玩法指标（建议手工统计）

- 单局时长 10–30 分钟；
- 玩家在一局中至少使用 2 种动作（发言/公开/指控/调查/私聊）；
- 线索板/笔记打开率 > 50%；
- 复盘页导出/观看率 > 30%；
- 玩家能说出“我为什么怀疑某人”的具体线索。

- 3 分钟内能展示：生成 → 选角 → 与 AI 对话 → 投票 → 复盘；
- 至少一次 AI“有性格的发言”和一次“信息差反转”；
- 复盘卡能在一屏内说清“真凶 / 你的指认 / 结果”。

## 9. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 私聊/搜证改动图，回归风险 | 高 | 新功能用独立节点 + 条件边；旧路径保持；新增图级 fake-LLM 测试 |
| AI 助手泄露真相 | 高 | 输入白名单（只给公开线索+笔记）；prompt 明确禁止；输出后做关键词过滤 |
| 场景生成 token 增加 | 中 | 地点数量上限 4；失败自动回退旧剧本 |
| 预设剧本内容质量 | 中 | 人工审 3 个短剧本；增加 validators 校验 |
| 视觉改造耗时 | 中 | 只做 CSS/组件，不换技术栈 |
| 答辩现场 API 慢 | 高 | 录屏 + 预设剧本 + 本地缓存 |

## 10. 最终建议

如果只做一件事：**做 AI 侦探助手**。
它不改变架构、不增加测试负担、演示效果明显，而且直接回应“AI 到底帮玩家做了什么”。

如果做两件事：**AI 侦探助手 + 场景搜证地图**。
这两项分别补“AI 辅助”和“侦探动作”，是参考项目里性价比最高的组合。

如果做三件事：再加 **私聊**，但放到答辩后，确保图结构和测试稳定。

**不建议**在答辩前做：React 重写、3D/语音、RAG/向量数据库、证物组合。它们不是不能做，而是**投入产出比不适合当前时间点**。
